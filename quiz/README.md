# CIT @ ROMA Lab · v5.3

实验室科研气质自评（Cultural Insight Test）。纯静态、纯前端，学生端 `index.html`，导师端 `faculty.html`。

## 题库与口味是两件事

| | 回答什么 | 放在哪 | 谁改 |
|---|---|---|---|
| **题库** | 这个选项**体现什么特质**（`dims`，六维 0–3） | `core.zh.json` / `extended.zh.json` | 改题的人 |
| **口味** | 我们**喜欢什么样的人**（`preference`，每选项 0–3） | `tastes/<id>.json` | 换机构 / 换取向的人 |

v5.1 之前这两样混在题库的 `score` 字段里，结果是题库看起来「自带标准答案」——其实那只是 ROMA Lab 一家的偏好。
分开以后：**同一个题库可以服务不同机构的不同取向，改口味不用碰题。**

口味的细节见 [`tastes/README.md`](tastes/README.md)。

| 文件 | 作用 |

## 计分口径

1. **题内相对分**：每题按「所选选项在该维的取值 ÷ 该题该维最大值」归一，再对有该维的题取平均。
   这一步**只看 `dims`，不看口味**——六维描述的是「你是什么样的人」。
2. **三点基线中心化**：
   - `floor` = 每题「选项最小值/最大值」的均值 → 每题都选最差 = 0 分
   - `base`  = 每题「选项均值/最大值」的均值 → 随机作答期望 = 50 分
   - `top`   = 每题「**口味分最高**的选项在该维的取值/最大值」的均值 → 本题可达到的上限 = 100 分

   `top` 不一定是 100：有些题「最贴合实验室取向的答案」并不是该维表现最突出的答案。
   如果直接拿 100 当归一上限，一份每题都选最优的作答反而只能拿到 60–73 分——v5.0 早期版本就是这个毛病，已修。
3. **换口味会挪动刻度**：`top` 依赖口味文件，所以同一份作答在不同口味下 `per` 会小幅变化。
   这是设计使然——「100 分」的定义里本来就含价值判断。报告同时记 `bankHash` 与 `tasteHash`，
   导师端能分清「分数变化」是因为题目变了还是口味变了。
4. **满分可达，但满分就是红旗**：v5.2 起口味为强制排列（每题最优解唯一），50 题全部押中实验室口味
   可以拿到 Fit 100。纯静态架构下口味表可以被技术手段直接下载，**保密不是防线，识别才是**：
   正常学生的最优押中率约七成封顶（真实样本 35/50），满分或近乎满分本身就是异常信号。
   导师端用「押中率 ≥90% + 总用时 + 改答次数」联合判定，打出「疑似预先获取评分表」的红旗，
   提示面试时就具体题目追问取舍理由。文字表面策略同样过不了契合线
   （实测见 `tools/philosophy_audit.py` 第 2 节）。
5. **可测性守卫**：某维有效题 < 8 道或题库里该维无区分题时，该维输出 `null`（未测量），不再显示成满分。
6. **分辨率守卫**：`top - base < 12` 的维度标 `resolution: 'coarse'`，页面上注明「可分辨区间偏窄，宜看趋势」。
   固定 50 题后六维区间都在 12 分以上，当前无维度触发。

## 只有一种模式：固定 50 题

v5.0 起取消了 20 题简版。理由不是「50 好看」，而是题量直接决定可分辨区间：20 题版里抗压维
`base→top` 只剩 6.0 分，等于把小数点后的噪声放大成几十分，测出来的人与人差异主要是随机波动。
**测不准的短版比不测更糟**——它会给出一个看起来精确、实际无意义的分数。

`scoring.js` 里 `BANK_FILES` / `TOTAL_ITEMS` 是唯一口径；`app.js` 载入时会校验题数，不等于 50 直接报错。
报告里的 `mode` 字段保留但恒为 `'full'`（历史兼容）。导师端遇到 v4.3 的 20 题简版报告会明确标注
「不可横向比较」，不当成「缺答 30 题」处理。

六个维度：BND 分寸感 / COM 沟通 / EMP 同理 / INT 诚信 / CRE 创造 / RES 抗压。
权重：0.20 / 0.20 / 0.17 / 0.25 / 0.09 / 0.09。`ROMA Fit` 只统计可测维度并按实际参与维度重新归一。

## 每次改题库必须做的事

```bash
python3 tools/extract_taste.py --check   # 0. 口味与题库仍绑定（改题后这步会先失败，属预期）
python3 tools/audit.py                   # 1. 质量审计，必须 PASS
node tests/scoring.test.js               # 2. 内核与迁移测试
node tests/e2e.mjs                       # 3. 真实浏览器端到端（需本机 Chrome）
```

改完题库后口味一定失配，此时要么用 `rekey.py --write` 重新生成，要么手工合并 `preference` 并重算 `taste_hash`
（步骤见 `tastes/README.md`）。

## 每次改口味必须做的事

roma v2 起每题四选项分值必须是 **0-3 的排列（互不相同）**，`bindTaste()` 会强制校验，违反即拒绝加载。
逐题取舍的依据写在 `tastes/roma-v2-设计说明.md`（改动请先读它）。

```bash
# 手改 tastes/roma.json 的 preference 后：
python3 tools/extract_taste.py --rehash  # 0. 校验排列规则并重算指纹（必须先过这关）
python3 tools/extract_taste.py --check   # 1. 绑定与覆盖校验
node tests/scoring.test.js               # 2. 内核测试（含位置均衡、可分辨区间）
node tools/calibrate_risk.js             # 3. 风险系数复核（优秀<20 / 最差>70 / 乱点>40）
python3 tools/philosophy_audit.py        # 4. 作弊策略与位置偏倚复查
node tests/e2e.mjs                       # 5. 浏览器端到端
```

审计的硬指标：

- 每个维度 ≥ 10 道可区分题
- 校准后随机作答区间跨度 ≥ 40 分
- 维度间最大非对角相关 |r| ≤ 0.6（防止把维度做成互斥）
- 各位置平均**口味分**极差 ≤ 0.25（防止位置偏倚）
- 潜变量回收率 ≥ 0.40
- 校准参数必须满足 `floor < base < top ≤ 100`（每维 100 分真实可达）

另有**设计理念**体检（不参与 PASS/FAIL，但每次大改题库都该看一眼）：

```bash
python3 tools/philosophy_audit.py
```

它回答的是另一个问题：一个不懂口味的聪明学生，能不能靠表面策略拿高分？关键指标：

- 选项字数与口味分的秩相关 |r| < 0.15；「最长即最优」的比例接近随机 25%
- 作弊策略（最长 / 最短 / 尽责词最多 / 永远选 A）的 Fit 不应过契合线
- **题内口味分与「六维总和」的秩相关**：越高说明「面面俱到」越通吃，与「必须取舍」的设计相反
- **口味最优解在六维中并列第一的维度数**：接近 6 说明最优解全面碾压，没有取舍
- 单题决定性：改一题能让 Fit 掉多少（掉太多说明该题单独决定结论）

## 导师端风险指标的标定

四项风险（公开表达 / 诚信 / 波动 / 利己）是启发式提示，系数写死在 `faculty.js`，口径记在
`rules.weights.json` 的 `risk_formulas`。改动系数、或**换了口味文件**，都必须跑：

```bash
node tools/calibrate_risk.js
```

判据：十种作答画像下，「优秀」画像四项都 < 20%，「乱点」诚信 ≥ 40%（提示作答可信度），
「最差」诚信与利己 ≥ 70%。v4.3 遗留的旧系数（严重 ×18 + 轻微 ×7）是按「200 个选项全 1 分」的
退化题库写的，套到 50 题新题库会让正常作答直接顶到 100%，已按仿真重标。

## v5.3 的三件新事

1. **押中率红旗（诚实性防线）**：口味表在纯静态架构下可被技术手段下载，保密不是防线——识别才是。
   导师端对每份报告计算「最优押中率 + 总用时 + 改答次数」，规则见 `rules.weights.json` 的 `gaming_rule`：
   押中 ≥98%（或 ≥90% 且 <4 分钟且零改答）打「疑似预先获取评分表」红旗，≥90% 且偏快/零改答打提醒。
   参照系：真实学生样本 35/50 押中、6.4 分钟、改答 1 次。
2. **学生端体验修复**：进度自动暂存 localStorage，刷新/误关页面后可选择继续上次作答，提交后自动清除。
   （曾试做「选后 700ms 停留窗口」，实测回退：停留会掩盖「快速糊弄」的作答信号，改答靠「上一题」回退即可。）
3. **隐私边界明示**：导师端 AI 测评报告（DeepSeek）按钮旁注明数据去向，发送前再做一次姓名脱敏
   （payload 本就不含 `name`，脱敏是纵深防御）；学生端隐私说明同步写明这一条。

另：CI 已上线（`.github/workflows/cit.yml`），push 触及 `quiz/` 即自动跑绑定校验/审计/单测/理念体检/标定/端到端。

## 报告与版本治理

导出的 JSON 带四个对账字段：

| 字段 | 含义 |
|---|---|
| `bankHash` | 题库指纹，只由 `qid + option + dims` 计算 |
| `tasteId` / `tasteHash` | 用的是哪一套口味、它的指纹 |
| `bankVersion` | 题库版本 |

导师端载入时分别判断：

- **题库指纹一致** → 直接采用，并独立重算一遍核对；
- **题库指纹不一致** → 按当前题库重算并告警（原报告的 `per` 不再采信）；
- **口味指纹不一致** → 六维分数仍可比（那只由 `dims` 决定），但 `ROMA Fit` 与四项风险是按现行口味重算的，单独告警；
- **没有 `bankHash`**（v4.3 及更早）→ 用 `migration_v4.3.json` 把选项字母按题干文本映射过来后重算，并明确标注「旧报告」。

v4.3 的「创造与抗压（CRV）」维度存在已知缺陷：50 题中有 22 题的四个选项 CRV 分值完全相同，
导致该维度对任何作答恒为 100%。已拆分重键为 CRE / RES，旧报告的该分数不可引用。
